SLIDE 5
Programming to Error/Return Codes
When methods return error codes or Boolean, you are responsible for handling all errors, all the time for every method call through the entire call chain
Failure to do so compromises the stability and error reporting of the entire system
So it is common to ignore error codes and hope nothing goes wrong!
The compiler can’t enforce/check that you to consume the return code from methods you’ve called. Errors codes can be easily ignored
If statements for nearly every functional line of code, thus adding code complexity
In this model of programming, if the API you’re calling fails, the program will muddle on with incorrect results or crash or corrupt data elsewhere. This makes finding the root-cause extremely difficult

SLIDE 6
Programming to Exceptions
changes your Assumptions
Errors throw Exceptions and this translates to methods returning valid data or not returning at all
Simplifies code such that you can reason about the flow of code
If you’ve reached “Here”, then everything before this was successful
A method either returns what it states or does not return
A standardized way to communicate error conditions, no matter what the construct (constructors, properties or methods).
Exceptions promote API consistency
Allow you to separate error-detection code from error-handling code
Fail fast and fail Visibly

SLIDE 7
Programming to Exceptions
changes your Assumptions
With (well written) Programming to Exception based code – unexpected exceptions eventually cause the unhandled exception handler to be called. This is where the exception gets logged
Typically uncover bugs in your application or scenarios that need to be accounted for, such as additional validations of input data
Exceptions  promote instrumentation because they are a well defined method-failure model. Tools such as Performance Monitor, Profilers, Debuggers etc. are all aware of Exceptions
The true power of exceptions though, lies in not handling them.

SLIDE 9
Exceptions & Performance

 use error codes because of concerns that exceptions might affect performance negatively.
Tester-Doer Pattern
CONSIDER

✓

 use the prefix "Try" and Boolean return type for methods implementing this pattern.
✓
DO
 provide an exception-throwing member for each member using the Try-Parse Pattern.

SLIDE 10
Exception Catching guidelines
A Method should only handle those exceptions it truly understands
Either to translate the Exception to another Exception Type and throw (include original as inner)
Or handle in some other way and Throw the original Exception
Use UEFs only in the “front end” of the application and only if the default handling is not sufficient
